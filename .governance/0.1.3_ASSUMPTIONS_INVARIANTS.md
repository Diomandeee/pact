# INVARIANTS & ASSUMPTIONS

Every invariant below carries a **Canary**: a mechanical detector that fires
when the invariant is violated. An invariant without a canary is a promise,
and this project exists because promises about prompt systems are exactly what
cannot be checked.

The canaries are gates. They run in CI. A violated canary fails the build.

---

## Invariants (must never be violated)

### INV-1: The engine is pure

- **Statement:** `pact-core` depends on nothing beyond `std` and performs no
  I/O, no network, no filesystem, no clock.
- **Why:** The math must be provable in isolation. The moment the engine can
  read a file, its behaviour depends on the world and every result becomes
  conditional on a state nobody recorded.
- **What breaks:** Every claim the analysis layer makes. If the engine is
  impure, a barcode is a measurement of the filesystem, not of the corpus.
- **Canary:** `cargo tree -p pact-core` lists zero dependencies, and
  `grep -rE "std::(fs|net|io|time|process)" crates/pact-core/src` returns
  nothing. Both run in CI.

### INV-2: Conservation

- **Statement:** Resources are created only at Sources and Broadcast gates,
  and destroyed only at Drains and lossy Converters. For every type `t`:
  `created[t] == destroyed[t] + held[t]`.
- **Why:** A simulation that quietly loses work will quietly tell you a
  pipeline is fine when it is dropping half its input. Silent loss is the
  failure mode that cost twelve hours on the MotionMix mirror, and it is the
  same shape here.
- **What breaks:** Pressure, starvation, and every economy diagnostic.
- **Canary:** `Ledger::conserved()` is asserted after every step in the
  property tests, per type, not in aggregate. An aggregate check would pass
  while two types swapped.

### INV-3: Reproducibility from seed

- **Statement:** The same graph and the same seed produce the same trace,
  byte for byte, forever.
- **Why:** A stochastic run you cannot replay is a run you cannot debug, and
  evidence built on an unreplayable run is not evidence. Also: barcodes are
  compared across generations, and comparison requires that a difference
  means something changed rather than that the dice rolled differently.
- **What breaks:** Persistence. Every bar becomes suspect.
- **Canary:** A property test runs the same graph twice with one seed and
  asserts trace equality. Iteration order is `BTreeMap` everywhere for this
  reason; a `HashMap` in the hot path is an INV-3 violation even if the test
  happens to pass.

### INV-4: Protocols validate before they generate

- **Statement:** Every protocol ships a validator, and its generator emits
  only graphs its own validator accepts.
- **Why:** A protocol is fundamentally a predicate on graphs. If generation
  comes first there is no way to say whether a hand-authored graph is a legal
  instance, which is the main use case: pointing the tool at something that
  already exists.
- **What breaks:** The decomposition half of the product. Import becomes
  unverifiable.
- **Canary:** For every protocol `P`, a property test asserts
  `P::validate(P::emit(args)).is_ok()` across generated inputs.

### INV-5: Determinism on predicates, never on effects

- **Statement:** Every gate, invariant check, and validator is deterministic.
  No check may call a model, hit a network, or depend on wall time.
- **Why:** An iteration is a model doing work and will never be
  deterministic. Contract discipline is only meaningful if the *checking* is
  reliable even when the *doing* is not.
- **What breaks:** The revert semantics. A non-deterministic gate makes
  "this generation is rejected" a coin flip.
- **Canary:** The analysis crate has no async, no network dependency, and its
  tests run with the network namespace unavailable in CI.

### INV-6: No stubs pass a gate

- **Statement:** No item in the living checklist may be ticked while its
  implementation returns a placeholder, `todo!()`, `unimplemented!()`, or a
  hardcoded success.
- **Why:** This is the one Mohamed named explicitly, and it is the failure
  that makes a checklist worse than no checklist: a ticked box that is not
  true converts uncertainty into false confidence.
- **What breaks:** Everything downstream trusts the checklist.
- **Canary:** CI greps for `todo!`, `unimplemented!`, `unreachable!("stub")`,
  and `#[ignore]` in non-test code, and fails on any hit. Separately, every
  checklist item names an artifact, and a gate script asserts the artifact
  exists and is non-empty. This is the same cold-artifact check the loop
  harness already runs on generations.

### INV-7: Rail and pulse are words, not primitives

- **Statement:** `pact-core` contains no type named Rail, Pulse, Phase,
  Track, or Generation.
- **Why:** The platform hosts many protocols. A protocol baked into the
  engine is privileged over every other one, which is precisely the thing
  that makes a tool useless to anyone whose workflow differs.
- **What breaks:** The claim that the platform is general. Also the ability
  to import someone else's corpus.
- **Canary:** `grep -riE "\b(rail|pulse|phase|track|generation)\b" crates/pact-core/src`
  returns nothing outside doc comments.

### INV-8: Dependencies live at L4

- **Statement:** `pact-algebra`, `pact-corpus` and `pact-analysis` depend only
  on other workspace members and `std`. Only `pact-cli` and `pact-server` may
  take third-party crates.
- **Why:** INV-1 keeps the engine pure and says nothing about the layers above
  it. The surface is where the outside world is allowed in, and if that is a
  habit rather than a rule it survives exactly until the first afternoon
  somebody wants a convenience in the analysis layer.
- **What breaks:** The claim that the analysis is portable. A corpus tool that
  drags a web framework into its homology is one nobody can embed.
- **Canary:** `cargo tree -p pact-analysis --depth 1` lists only workspace
  members, and the same for `-algebra` and `-corpus`.

## Assumptions (believed, could turn out false)

### ASM-1: Every non-trivial chain factors as a degenerate railpulse

- **Confidence:** Low. Suggestive evidence only.
- **Evidence for:** 11 of 11 chains show at least one canonical stage; the
  two missing stages across the corpus are exactly the two combinators with
  no implementation.
- **Why it is weak:** The falsification predicate used in finding 0001 could
  not have failed. Nearly every chain contains a `⊗`, so almost nothing could
  have refuted it.
- **What would settle it:** Define the rewriting relation, then test whether
  every word rewrites into `↺(⊗ ▸ * ▸ ⊕)` with stages set to identity. Until
  that exists this stays an assumption.
- **If false:** railpulse drops from L1.5 to one protocol among many, and the
  algebra needs a seventh combinator. The platform survives; the marketing
  story changes.

### ASM-2: Simulation predicts execution

- **Confidence:** Medium.
- **Statement:** A graph that starves in simulation will starve in execution,
  and one that flows will flow.
- **Why it might be false:** Simulation moves synthetic tokens on a clock.
  Execution dispatches agents whose latency, failure modes, and partial
  outputs have no analogue in the token model.
- **What would settle it:** Run the same graph through both interpreters on a
  real corpus and compare starvation sets.
- **If false:** The shared-interpreter design still holds, but simulation
  becomes a design aid rather than a predictor, and the product claim
  narrows.

### ASM-3: The SOOP-2 types are accurate

- **Confidence:** Medium-low.
- **Statement:** The 144 declared `input_type` / `output_type` pairs describe
  what the skills actually consume and produce.
- **Why it might be false:** They were authored by hand, and nothing has ever
  checked them against behaviour. Nine skills consume `M^n`, which nothing
  produces; that is either a real gap or a mislabelling.
- **What would settle it:** Instrument execution and compare declared types
  against observed artifacts.
- **If false:** Every number in finding 0001 shifts. The method survives, the
  measurements do not.
