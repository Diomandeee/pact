# IMPLEMENTATION GUIDE

How to work in this repository. Short on purpose; a guide nobody finishes is a
guide nobody follows.

## The layer rule

```
L4  surfaces      CLI, export, API
L3  importers     SOOP-2 corpus, chains, logs → graph
L2  analysis      statics · dynamics · structure · persistence
L1  algebra       the six combinators, protocols
L0  engine        typed tokens, nodes, two edge kinds, simulation
```

Dependencies point one way: `L4 → L3 → L2 → L1 → L0`. **`pact-core` depends on
nothing.** Not on a logging crate, not on serde, not on a clock. INV-1 has a
canary and it runs in CI.

L2 comes after L3 deliberately. Analysis with no real corpus produces
beautiful metrics over synthetic graphs and never meets a fact that can
contradict it.

## Port, do not reinvent

Four Python references exist and their behaviour is pinned by tests:

```
~/.claude/skills/divergent-rail/scripts/loop_harness.py     homology, 9/9
~/.claude/skills/divergent-rail/scripts/prompt_algebra.py   the category
~/.claude/skills/divergent-rail/scripts/prompt_economy.py   the economy
~/.claude/skills/divergent-rail/scripts/decompose.py        the factoring
```

Every L2 and L3 gate reads "matches the Python." That turns the rewrite into a
differential test. A rewrite with no oracle is how behaviour silently changes,
and there is no reason to accept that risk when working references exist.

When the Rust and the Python disagree, **do not assume the Rust is right.**
Find out which one is wrong. Twice so far the older implementation has been
correct.

## The gate discipline

A checklist item is ticked because its Gate command passed. Never because the
work feels done.

**A gate that cannot fail is not a gate.** Finding 0001 shipped with a
falsification test too weak to have failed, and said so in the document. Do the
same. If a gate could not have caught the thing it claims to catch, write that
down instead of ticking the box.

**Blocked is not failed.** If an item cannot proceed because its prerequisite
does not exist, name the missing prerequisite and stop. Retrying cannot create
a boundary. Substituting a stub to keep moving is the single most tempting move
in a checklist-driven build, and INV-6 exists because of it.

## The lock map

```
./scripts/pz status       what is open, what is next, what is far and why
./scripts/pz check        nothing was edited while locked
./scripts/pz open <path>  unlock a file whose gates have passed
```

A locked file is not a stub. A stub claims to work and turns a red gate green.
A locked file declares it is closed and keeps the gate red. If you find
yourself wanting to delete a lock header, the honest move is to go pass the
gate.

## Commit ritual

```bash
./scripts/pz check          # did I work ahead of a gate?
./scripts/canaries.sh       # do the invariants still hold?
cargo clippy --workspace --all-targets -- -D warnings
cargo test --workspace
```

CI runs `pz check` **first**. Working ahead of a gate should fail before the
build gets a chance to be green.

A red signal left red is fine and expected. A red signal made green by
weakening the check is the failure this whole structure exists to prevent.

## Comments

Explain **why**, not what. The code says what.

The bar: a comment earns its place if removing it would let someone
reintroduce a bug that has already happened once. `Demand::All` carries a note
about why half-run is worse than not-run. That is the standard.

## Numbers in prose

Any claim in a document, commit message, or finding that could be checked must
say how it was checked. "Nine skills can never fire" is fine because
`prompt_economy.py` prints them. "The corpus is well structured" is not a claim,
it is a mood.

## When you disagree with this guide

Change it, in a commit that says why. It is a governance document, not
scripture. What it must never become is a description of how the project used
to work.
